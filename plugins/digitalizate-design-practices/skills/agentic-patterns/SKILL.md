# agentic-patterns

Same mechanics as `ux-library`, different domain. Generated by `/ux-sync`; do not edit `index/` or `references/` by hand.

- `index/_overview.md` — counts, subcategories, goals, tags.
- `index/by-category/agentic-patterns.md` — one line per pattern, grouped by subcategory, pointing to its reference file.
- `references/agentic-patterns/<subcategory>.md` — full entries (why, **Do.** steps with do/don't, measure, sources, wireframe, Notion link).

## How to use

1. Name the problem in agent terms: what the agent must decide, what it can touch, what can go wrong, who supervises. Pick two or three subcategories from the overview.
2. Read those index sections, shortlist by score and `use:` context, then open the entries. Scores here skew lower than the UX library (many are research-stage); treat 3 as "worth considering" rather than "situational".
3. When recommending a pattern, cite `AGP-012 Pattern name` and name the **Don't** items that apply to the user's setup. Avoid-when contexts matter more here than in UX: a pattern for long-running autonomous agents is wrong for a stateless chat feature.
4. Patterns about alignment, monitoring, security and privacy are design-level guidance. They do not replace a real threat model, evaluation suite or legal review; say so when the stakes are high.

## Boundary with ux-library

If the question is how a person sees, trusts, interrupts or corrects an agent on screen (progress, confirmations, undo, explanations, error recovery), that is interface work: use `ux-library` (feedback-and-error-handling, workflow-and-multi-step-processes, build-trust goal) and bring in this skill only for the agent-side mechanism.
