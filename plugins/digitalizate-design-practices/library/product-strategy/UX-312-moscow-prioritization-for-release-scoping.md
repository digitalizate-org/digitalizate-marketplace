## Why
Categorize feature requirements as Must-Have (non-negotiable for release), Should-Have (important but a workaround exists), Could-Have (nice if time allows), and Won't-Have (explicitly excluded from this scope). MoSCoW creates a shared language for scope conversations with stakeholders and prevents the common failure mode where everything is labeled "critical" — making genuine priority invisible. The discipline of distinguishing Must-Haves from Should-Haves is where most of the value of MoSCoW lives.

## How to implement
- Apply MoSCoW at the start of each release planning cycle.
- Must-Haves should represent the minimum viable product — what would make the release not worth shipping without.
- Must-Haves should consume no more than 60% of available capacity, leaving room for Should-Haves and buffer for unexpected complexity.
- Force explicit justification for every Must-Have label.
- Document Won't-Haves as explicitly out of scope (not just unmentioned) to prevent scope creep from assumed inclusions.

## Metrics
Applying this pattern can positively influence the following UX metrics:
- **Effectiveness**: Completion rate, Task success rate
- **Efficiency**: Time saved per task, Completion time
- **Satisfaction & Perception**: CSAT, Satisfaction rating
**How to measure**: Compare task success rates and user satisfaction between releases scoped with MoSCoW versus unconstrained releases. Track post-launch support tickets and usability test error rates to confirm that must-have features are polished and functioning, validating the prioritization criteria.
